## 疑問→理解のラリー

### `INT_MAX` を超える入金をどうするか
- 理解: 足す前に、引き算で余裕を確かめる（`fee > INT_MAX - liquidity`）
  - `liquidity + fee > INT_MAX` と書くと、その足し算自体があふれて未定義動作になる
  - `INT_MAX - liquidity` は、両方が 0 以上なら安全
- 2つの検査を両方済ませてから更新する。片方だけ増えた状態で例外が出ると、手数料だけ取られたことになる
- 例外は `<stdexcept>` の `std::overflow_error` で足りる

### 名前が回りくどい
- `net` は「手数料を引いた後の額」（net amount、手取り）。対になるのは gross（引く前）
- 一番効いたのは引数の `value` → `amount`。`it->second->value += value - ...` と、残高と入金額が同じ名前で並んでいたのが読みにくさの原因だった
- `deposit` の中なので `deposit_` は重複。`truncated` は整数の割り算を見ればわかるので、名前から外した

### エラーメッセージの文面
- 最初の案 "deposit would exceed the maximum amount" は、1回の入金額の上限に読める。引数の `amount` とも紛らわしい
- 理解: あふれるのは入金額ではなく、溜まっている側。何があふれたかを言う
  - "deposit exceeds the bank's liquidity capacity"
  - "deposit exceeds the account's balance capacity"

### 関数がごちゃついて見える
- 原因は検証の数ではなく、計算と検証が1行ずつ交互に並んでいたこと
- `amount <= 0` だけは計算結果を使わないので先頭に残す。残りは `fee` と `credited` を出した後にまとめる
- 分割はしない。1つの機能に収まっている

### 割り算を先にする式が読みにくい
- `amount / 100 * P + amount % 100 * P / 100` は正しいが読めない
- 最初は「料率を `deposit` に直書きしたほうがまし」と思った。しかし `amount * 5 / 100` と書いてもあふれる。問題は定数の置き場所ではなく、掛け算を先にしていること
- 理解: 5% は 1/20 なので、20 で割れば掛け算がいらない。結果は切り捨ての `amount * 5 / 100` と同じ
- 他の案: `long` に広げて計算する（`long` が64ビットの環境に依存する。C++98 には `long long` がない）

### `operator[]` を public にしたら `private: class Account;` が必要になった
- 理解: `operator[]` が `const Account&` を public に返す時点で、`Account` は公開インターフェースの一部
  - private のままだと、外から `Bank::Account` という名前が書けない。C++98 には `auto` がないので、`const Bank::Account& acc = bank[0];` と変数に受けられない
  - public にしても、コンストラクタと属性が private なので、外からは作れないし書き換えられない
- 内部クラスは、宣言と定義で同じアクセス指定にする必要がある

### `Account` を別ファイルにできるか
- できる。`Bank.hpp` に `class Account;` とだけ書き、`Account.hpp` で `class Bank::Account { ... };` と定義する
- 勘違いしていたこと: `Account.hpp` に単独の `class Account` を書いて `Bank` の中で前方宣言しても、それは `Bank::Account` という別のクラスになり、結び付かない
- やめた理由: `Account.hpp` は `Bank.hpp` なしで成り立たない。分けても独立した部品にならない

### 循環参照にならないのはなぜか
- 疑問: `Bank.hpp` に `typedef std::map<size_t, Account *> Accounts;` を書くのだから、`Account` の定義が要るはず
- 理解: **ポインタか参照で持つなら宣言だけで足りる。値で持つなら完全な定義が要る**
  - ポインタの大きさは、指す先が何でも同じ。`map` は `Account` の中身を知らずに作れる
  - 中身が要るのは `it->second->value` や `new Account(id)` で、これは関数本体にしか出てこない。本体は `Bank.cpp` にある
  - `std::map<size_t, Account>` と値で持つと、`Bank.hpp` が定義を必要として循環する
- 証拠は分割前のファイルにあった。`class Account;` の宣言の後、定義より前に `typedef` を書いて通っていた

### `Bank::` を2回書く
- `Bank::Accounts::iterator getAccount(size_t id)` と書いて「`Accounts` は private」と怒られた。`Accounts` を public にするべきか迷った
- 理解: 関数名の前の `Bank::` が抜けていた。`Bank` と無関係な関数だと解釈され、外から private な型を使ったことになっていた
  - 関数名の前の `Bank::` は、メンバ関数の定義なら必ず要る
  - 戻り値の前の `Bank::` は、戻り値が `Bank` の中の型のときだけ追加で要る。コンパイラは左から読むので、戻り値を読む時点ではまだ `Bank` の中の話だとわからない

### friend 関数を `.cpp` で定義する
- `friend std::ostream& Bank::operator << (...)` と書いて「`friend` はクラスの外で使えない」と怒られた
- 理解: `.cpp` では `friend` も `Bank::` も付けない
  - `friend` は「この関数に private を見せる」というクラス側の許可。書けるのはクラスの中だけ
  - friend 関数は `Bank` のメンバではなく、外にある普通の関数。本体で `Bank` の中の名前を使うときは `Bank::Accounts` と書く

### `return (p_os);` がエラーになった
- 原因はタブとスペースの混在。`for` の行はスペース4つ、`return` の行はタブ1つだった
- コンパイラはタブを8桁と数えるので、`return` が `for` の中にあるように見える。その警告（`-Wmisleading-indentation`）が `-Werror` でエラーになった
- 昨日「エラーではないが直す箇所」に書いた混在が、実害になった

### `createAccount` のリーク
- `clientAccounts[id] = new Account(id);` は、`Account` の確保に成功した後に `map` 側の確保で失敗すると、`Account` が解放されない
- 疑問: `new` も失敗するのだから、`new` も `try` で囲むべきでは
  - 理解: 囲まなくていい。`new` が失敗したときは何も確保されていないので、片付けるものがない。`try` / `catch` が要るのは、失敗したときに自分で片付けるものがある場所だけ
- 疑問: `Bank` の中でメッセージを出したほうが親切では
  - 理解: 出すのは `main`。`createAccount` は ID を返す関数で、中で受けても返せる ID がない。画面に出すかどうかは呼ぶ側が決めること
- 疑問: 例外が `main` まで届いたらクラッシュするのだから、リークは関係ないのでは
  - 理解: `main` が `catch` すればプログラムは続く。続くからリークが残る。`Bank` のデストラクタは `map` に入っている口座しか消さない
  - 例外で関数を抜けるときに自動で片付くのはローカル変数だけ。ポインタ変数は消えるが、その先に `new` で作ったものは消えない
- 分岐するのは `main` ではなく `createAccount` の中。`main` には `new` の失敗も `map` の失敗も同じ `bad_alloc` として届く
- 学び: **確保したものを自分しか知らない間は、失敗したときの片付けも自分の責任**
