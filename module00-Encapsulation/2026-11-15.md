## 学んだこと: Makefile

### 基本の形
- `ターゲット: 材料` の次の行にコマンドを書く。コマンド行の先頭は TAB（スペースだと `missing separator`）
- 材料がターゲットより新しいとき、またはターゲットが無いときだけコマンドが走る
- `$<` は材料の 1 個目、`$@` はターゲット名。`%.o: %.cpp` の中では `Bank.cpp` と `Bank.o`

### `$(NAME): $(OBJS)` の動き
1. `bank` の材料は `main.o Bank.o Bank_test.o`
2. 各 `.o` が無いか古ければ、`%.o: %.cpp` のルールでコンパイルする
3. `.o` のどれかが `bank` より新しければリンクする
- `.o` は毎回作られるわけではない。古いものだけ作り直される

### `.d` ファイルと `-MMD`
- `.d` は、コンパイラが書き出す「この `.o` はどのファイルに依存しているか」のメモ
- 中身は Makefile の構文そのもの（`Bank.o: Bank.cpp Bank.hpp`）
- `%.o: %.cpp` だけだと make は `.hpp` を知らない。`.d` があるので、`Bank.hpp` を変えると `Bank.o` が作り直される
- `-MMD` はコンパイルのついでに `.d` を書かせるフラグ。`<iostream>` などのシステムヘッダは載せない

### `-MP` と「空のルール」
- `-MP` を付けると、`.d` の末尾に `Bank.hpp:` という行が足される。材料もコマンドも無いルール
- ルールが無い場合: 「`Bank.hpp` の作り方がわからない」→ エラーで止まる
- 空のルールがある場合: 「作り方は知っている。やることは無い」→ 作ったことにして先へ進む
- 困る場面: ヘッダを改名・削除したとき。古い `.d` がまだ旧ヘッダを材料に挙げているので、`-MP` が無いと `No rule to make target 'Bank.hpp'` で止まる
- `-MMD` は「ヘッダを変えたら再コンパイル」、`-MP` は「ヘッダを消しても make が止まらない」ための保険

### `-include $(DEPS)`
- 2 段階ある
  1. `$(DEPS)` は**ファイル名の並び**になるだけ（`main.d Bank.d Bank_test.d`）
  2. `include` がそのファイルの**中身**をその場所に貼り付ける（C++ の `#include` と同じ動き）
- `.d` が Makefile の構文で書かれているから、貼るだけでルールとして機能する
- 先頭の `-` は「ファイルが無くてもエラーにしない」。初回や `make clean` の後は `.d` が無いので必要

### `.PHONY`
- 「この名前はファイルではなく命令の名前だ」と make に伝える宣言
- 無いと、`clean` という名前のファイルがあるだけで `'clean' is up to date` になり、`rm` が走らない
- `$(NAME)` は入れない。本物のファイルなので「最新なら何もしない」判定が必要。入れると毎回リンクし直し、「再リンクしない」ルールに反する

## 決めたこととその根拠

### getter は const 参照で返す
- 課題文 5 ページに「コピーで返す getter は認めない」とある。`int getValue() const` は値返しなので当てはまる
- 必須要件なので、ここを落とすとボーナスも採点されない
- `const int& getValue() const` の形に 4 つとも変えた

### テストは公開 API から見える振る舞いだけを確かめる
- `createAccount` のテストで「口座が 1 つだけ作られたこと」を map のサイズで確かめたくなったが、やめた
- 課題が求めているのは次の 3 点で、どれも今ある関数で確かめられる
  - 返ってきた id で口座を引ける
  - 初期状態が残高 0、借金 0
  - 2 つ作ると id が重ならない
- テスト用に `size()` を足さない。テストのためだけに公開面を広げると、「なぜこれが public なのか」を説明できなくなる
- `operator<<` の出力を文字列で比べる案も不採用。表示の文言を変えるたびにテストが壊れる
  - 出力を変数にする方法は `std::ostringstream oss; oss << bank; oss.str()`
  - 必要になったら `expectEqual` に `const std::string&` 版をオーバーロードで足す
- `bad_alloc` は単体テストで再現できないので、正常に作れることだけを確かめる

### 例外を確かめるテストの型
```cpp
try {
    bank.withdraw(id, 1);
} catch (const Bank::InsufficientFunds&) {
    return; // 期待どおり
}
throw std::runtime_error("withdraw: expected InsufficientFunds");
```
- 2 本目以降は、操作の行と例外の型を差し替えるだけ
- `catch` は参照で受ける（値受けだとコピーが起きる）
- 例外が出ないはずの操作は `try` で囲まない。`catch (...)` で受けて別の例外を投げ直すと、元の原因（`no such account` など）が消える。囲まなければ `main` まで届いて `e.what()` で表示される
- 戻り値を使わない呼び出しは `(void)bank[id];` と書いて、意図して捨てていることを示す

### 実装とテストを一緒に進める（ex01 から試す）
- 実装が全部終わってからテストを書くのは面倒だった。「どの検査が何を防いでいたか」を思い出す作業が上乗せされる
- 次からは「検査（または機能）を 1 つ書く → テストを 1 本書く → `make` で通す → コミット」の順で進めてみる
