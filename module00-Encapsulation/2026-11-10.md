## 疑問→理解のラリー

### 2行の重複は共通化するべきか
- 疑問: デストラクタの `delete it->second; clientAccounts.erase(it);` が `deleteAccount` と同じ。2行で「map 要素の削除」という1つの意味を持つので単位としては成り立ちそうだが、2行を切り出す意味があるのか
- 理解: 行数は基準にならない。見るのは3点
  1. **同じ理由で変わるか**。片方を直すとき必ずもう片方も直すなら共通化する。今たまたま同じ見た目なだけなら、後で片方だけ変えたいときに邪魔になる
  2. **名前を付けると読みやすくなるか**
  3. **間違えやすい知識を閉じ込められるか**（順番を守る必要がある、など）
  - 回数の目安は「2回目までは重複を許し、3回目で考える」
- 今回の結論: 共通化しない。2つは目的が違った
  - `deleteAccount` は map が生き続けるので、1要素を取り除く（`delete` + `erase`）
  - デストラクタは map ごと消えるので、指し先を解放するだけ（`delete` のみ）。要素は map 自身のデストラクタが片付ける
  - `erase` を外すと共通部分は `delete it->second;` の1行になり、切り出す対象がなくなった
- 見つかったバグ: ループの中で `erase(it)` すると `it` が無効になる。そのあとの `it++` は未定義動作

### `findOrThrow` という名前の違和感
- 疑問: 何を find するのか分からない。`findAccount` がいいのでは
- 理解: `findAccount` にすると「見つからなければ例外」が名前から消える。C++ の `find` は「無ければ `end()` を返す」という慣習と結びついているので、読む人は `end()` と比較が要ると思ってしまう
- 疑問: でも他の関数は例外を投げても `OrThrow` と付けない。非対称では
- 理解: 原因は `OrThrow` ではなく **`find` という単語**。`find` が「失敗しても投げない」を持ち込むので、打ち消しに `OrThrow` が要るだけ。`find` をやめれば `OrThrow` も要らない
  - `get` は「あるはずのものを取る、無ければ異常」と読める → `getAccount`
  - 標準ライブラリも同じ対比: `map::find` は `end()` を返し、`map::at` は `out_of_range` を投げる。`at` に `OrThrow` は付いていない

### デストラクタは誰が呼ぶのか
- 疑問: private ではだめなのか。Bank クラスが呼ぶわけではないのか
- 理解: 呼ぶのは**そのオブジェクトを破棄するコード**。ローカル変数なら、スコープを抜ける関数（今回は main）の中にコンパイラが呼び出しを挿入する。普通のメンバ関数と同じアクセスチェックがかかるので、private だと `Bank bank;` と書いた時点でエラー
  - `new` したものは `delete` を書いた場所、メンバ変数はそれを持つクラスのデストラクタが呼ぶ
  - `Account` のデストラクタを private にしても、`friend class Bank;` があるので Bank からの `delete` は通る
- 「デストラクタを private にする」記憶の正体: スタックに置かせず、専用の関数（`destroy()` で `delete this`）を通させる設計。コンストラクタを private にして生成の経路を絞るのと対。Bank には不要

### `gcc` でコンパイルしたら undefined reference が大量に出た
- 疑問: `operator<<` やデストラクタの名前が出ているので、そこが悪いのかと思った
- 理解: コードは悪くなかった。`gcc` は C++ 標準ライブラリをリンクしない。`g++`（課題の指定は `c++`）を使う
- エラーメッセージの読み方
  1. **誰が出しているか**。行頭が `/usr/bin/ld:` で最後が `ld returned 1 exit status` ならリンクエラー。コンパイルは成功している
  2. コンパイルエラーは `ファイル名:行:列: error:` の形。const や型の間違いは必ずこちらに出る
  3. `in function ...` は**原因の場所ではなく、使っている場所**
  4. **何が見つからないかの共通点を探す**。今回は `std::cout`、`operator new`、`__cxa_throw` など全部が標準ライブラリだった。自分の関数名が出ていたら、定義の書き忘れかコンパイル対象への入れ忘れ

### `iterator it = p_bank.clientAccounts.begin()` がエラーになる
- 疑問: `begin()` が `const_iterator` を返しているように読めるが、なぜそうなるのか
- 理解: `p_bank` が `const Bank&` だから、メンバの map も const 扱いになり、const 版の `begin()` が呼ばれる。昨日メモした `getAccount` の2本立てと同じ仕組みを、今日は自分で踏んだ
  - `const_iterator` は指している要素を書き換えられない（`const T*` 相当）。`const iterator` はイテレータ自体が動かせない（`T* const` 相当）
  - 長いエラーは `{aka ...}` を飛ばし、`conversion from 'A' to non-scalar type 'B' requested` の骨格だけ読む

### コピー禁止の引数はなぜ `const Bank&` なのか
- 疑問: `const Bank&` だけを private にして、非 const のオブジェクトからのコピーは防げるのか。引数が `const Bank&` なら const しか受け付けないべきでは
- 理解: 引数の `const` は呼び出し側への要求ではなく、**関数側の約束**（「受け取ったものを書き換えません」）。書き換えてよいオブジェクトを渡しても困らないので、非 const も const も渡せる
  - 実例: `operator<<(std::ostream&, const Bank& p_bank)` に、main の非 const な `bank` を渡せている
  - 自分で1つ宣言すると、コンパイラは別の版（`Bank(Bank&)` など）を生成しない。だから `const Bank&` 版だけで全部塞がる
- 疑問: `int *arg` に `int i = 1` を渡すと `0x01` と解釈するのと同じ話か
- 訂正: 別の話。それは型が違うものへの読み替えで、C++ ではエラー。const を足すのは、同じものを指したまま書き換えを禁止するだけ
  - 規則は1つ: **何も壊さない変換は通し、壊しうる変換はエラー**。const を足すのは通る、const を外すのはエラー、`int` → `int*` もエラー
- 疑問: `Bank&` しか private にしていない。アドレスからインスタンス化できるのでは
- 理解: `Bank*` を受け取るコンストラクタは定義していないので、できない。コンパイラが自動生成するのはデフォルトコンストラクタ、コピーコンストラクタ、コピー代入、デストラクタの4つだけ
  - `Bank&` は参照（別名。`a` と書いて渡す）、`Bank*` はポインタ（`&a` と書いて渡す）。型として別物で、自動変換されない
- **まだ消化しきれていない**: const を足す変換が自動で通ることに「一貫性がない」感覚が残っている。`operator<<` の中に `p_bank.liquidity = 0;` と書いてエラーを見ると、「その名前を通している間だけ書き換え禁止」の実物が見られる
