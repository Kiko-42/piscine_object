## 決めたこととその根拠

### `Graph` はサイズを `float` のまま持つ。マス目に直すのは `print` の中だけ
- 途中の案: コンストラクタで四捨五入して、整数の値を `size` に入れる
- やめた理由
  - 丸めた値しか持たないなら、`size` が `Vector2`（`float` 2 つ）である意味がない
  - 点は生の `float` のまま持っているのに、サイズだけ丸めて持つのは扱いがそろっていない
- 採用した解釈: `Graph` はデータ（連続した座標の世界）、ASCII は見せ方の 1 つ
  - マス目に直すのは、文字で出力するときだけの都合
  - ボーナスの PNG や線では、点 2.6 を 2.6 の位置に描ける。コンストラクタで丸めるとこの情報が消える
- 課題文には `float` の理由は書かれていない。これは自分の解釈

### マスの個数はサイズの切り上げ、点のマスは切り捨て
- S19 で決めた「サイズを四捨五入」を変更した
- 理由: `addPoint` は `point.x < size.x` で受け付ける。`floor(point.x)` は必ず `ceil(size.x) - 1` 以下になるので、`paper` の外に出ない
- 四捨五入だと出る: サイズ 2.4 → 幅 2（列は 0 と 1）。点 2.3 は受け付けられ、列 2 に書こうとする
- 点の表示も S19 の「四捨五入」から切り捨てに変更した（点 2.6 は列 2 に出る）

### 範囲の判断は使う人の考え方に合わせる
- 使う人は「サイズを 2.4 にしたから、2.4 より小さい点は入る」と考える
- 「マス目に直すと列が足りないから断る」は作る側の都合。`addPoint` では断らず、`print` の側でマスを足りるだけ用意する

### サイズ 0.4 は有効
- 「幅 0.4 の紙」として受け付け、1 マスで表示する
- コンストラクタの条件は `0 < size <= MAX_SIZE` のまま

### 行頭の `>& ` は出力に含める（S19 の未決を解消）
- 出力例と見比べられるので、同じ形にした

## 学んだこと（疑問→理解のラリー）

### コンストラクタの中の `size` は、引数とメンバのどちらか
- 背景: コンストラクタで丸めた値をメンバに入れ、そのあと `if` で範囲を検査した
- 起きたこと: サイズ 0.4 が検査を通り、0 × 0 のグラフができた
- 元になった疑問: 「NaN のテストが落ちるようになった」と思った（実際に落ちていたのは 0.4 のテスト）
- 理解
  - 引数とメンバが同じ名前のとき、コンストラクタの本体で `size` と書くと引数を指す。メンバは `this->size`
  - 検査していたのは丸める前の 0.4 で、丸めた後の 0 は見ていなかった
- 取り違えた理由: 失敗のメッセージがどのテストでも `size should be refused` だった。`testGraphSizeZero` は `testGraphSizeNaN` より先に走るので、NaN のテストまで進んでいなかった
- 対応: メッセージをテストごとに分けた

### 初期化リストは、本体の `if` より先に実行される
- 背景: 初期化リストに `static_cast<int>(std::floor(size.x + 0.5f))` と書いた
- 理解: NaN や無限大を `int` に変えるのは未定義動作。`if` で断る前に変換が走っていた
- 対応: 検査の前には変換しない（今は `print` の中で、検査を通った値だけを変換している）

### `static_cast` と `dynamic_cast` の違い
- 元になった疑問: 「`dynamic_cast` は無理やり変えるので、エラーに気づきにくい」と覚えていた
- 理解: 逆だった
  - `static_cast`: コンパイル時に型の関係だけを見る。値は見ない（NaN → `int` はコンパイルが通る）
  - `dynamic_cast`: 実行時に本当の型を調べる。違えばポインタは `NULL`、参照は `std::bad_cast`。親クラスに `virtual` 関数が要る
  - `reinterpret_cast`: 確かめずに、ビットの並びを別の型として読む
  - C の書き方 `(int)x`: 複数のキャストを順に試し、通ったものを黙って使う。気づきにくいのはこれ
- ex01 には継承がないので、使うのは `static_cast` だけ

### `std::floor` は `int` を返すのか
- 元になった疑問: `floor` が `int` を返すなら `static_cast<int>` は要らないのでは
- 理解: `std::floor(float)` は `float` を返す（3.7f → 3.0f）。`int x = std::floor(...)` が通るのは、暗黙の変換が起きているから
- `static_cast<int>` を付ける意味: 「ここで小数を捨てている」と読む人に見せる。`-Wconversion` を付けると、付いていない行は警告になる

### `floor(x + 0.5f)` は、それ自体が四捨五入
- 背景: `std::ceil` に変える理由に納得できなかった
- 考えたこと
  - サイズ 2.4 で `print` の幅が 2 なら、`addPoint` で弾けばよいのでは
  - それは作る側の都合で、使う人には不自然（上の「決めたこと」）
  - なら幅は 3 が必要。今のコードは `2.4 + 0.5` の四捨五入で 3 のはず。それなら落ちないはず → 説明と矛盾する
- 間違えていた箇所: `floor(2.4 + 0.5)` = `floor(2.9)` = 2。`+ 0.5` して切り捨てることが四捨五入で、さらに四捨五入すると 2 回かけたことになる
- 理解: 小数部分が 0.5 より小さいとき、四捨五入は切り上げより 1 小さい（2.4 → 2 と 3、0.4 → 0 と 1）

### 落ちたケースを、どうテストにするか
- 元になった疑問: 特定のサイズと特定の点の組なので、独立したテスト関数が要るのでは
- 理解
  - `paper[y][x]` の範囲外アクセスは未定義動作。普通のビルドでは落ちずに通ることがあり、テストにならない
  - `paper.at(y).at(x)` は範囲を確かめ、外なら `std::out_of_range` を投げる。毎回同じ結果になる
- テストが確かめる約束: 「`addPoint` が受け入れた点は、必ず `print` できる」
- 出力を画面に出さない方法: `std::cout.rdbuf(sink.rdbuf())` で差し替え、終わったら元に戻す
- 確かめたこと: `std::ceil` に直す前はテストが `print(): accepted point should be printable` で落ち、直した後は通った

### テストの値は定数から計算する
- 元になった疑問: `9.9f` より `MAX_SIZE - 0.1f` のほうがよいのでは
- 理解: `9.9f` は「`MAX_SIZE` が 10」を前提にしている。`MAX_SIZE` を変えると、テストの意味が変わる
