# Module 00 - Encapsulation / S3: 直接代入が弾かれるのを確認した（2026-11-05）

## やったこと
- Account を `class` にした。`id`・`value`・コンストラクタは全部 private（class の既定）。`friend class Bank;` で Bank だけが触れる
- Bank に `createAccount` / `deposit` / `withdraw` を足し、main の `accountA.value = 100` をこれらに置き換えた
- `private` にした時点で、元の main の `accountA.value = 100` が `g++ -std=c++98 -Wall -Wextra -Werror` でコンパイルエラーになるのを見た。これが「壊す呼び出しが弾かれる」1本目（テストはコンパイルエラーそのもの）

## 決定と理由
- **struct → class**: カプセル化の課題なので、既定が private の class を使う。struct のまま `private:` を足すと「隠す意図」が型の選択に出ない
- **アクセス指定子**: `private:` / `public:` はラベルで、次の指定子か `}` まで効く。インデントで範囲は決まらない。切り替えは何度でも可だが、データを先に private、関数を後に public でまとめる

## 疑問→理解
- 疑問: Bank を隠す意味が分からない。どこからでも操作できていいのでは。認証は今回の機能に無い
- 理解: **操作（public メソッド）は誰が呼んでもよい。隠すのはデータ**。この2つは別の軸
  - `bank.deposit(id, 100)` は誰でも呼べてよい
  - `bank.liquidity -= 200` や口座一覧への直接 push は塞ぐ。public のままだと「入金ごとに 5% を銀行が受け取る」「貸付は銀行の資金の範囲内」をメソッドを通さず回避できる
  - 認証（誰が呼ぶか）ではなく「ルールを通らない抜け道があるか」の問題。public メソッドがドア、private データは窓なし
- 今は Bank がまだ `struct` で `liquidity` が public（main に `bank.liquidity -= 200` が残っている）。次で塞ぐ

## subject の要件で見落としていたもの（S4 の題材）
- Account は **Bank の内部構造体**にすること（subject: "The Account structure must be internal to the Bank structure"）
- Account に作れるメソッドは **const の getter だけ**
- Bank は ID で口座を引く **operator[]** を持ち、while/for で探してはならない
- 銀行は入金ごとに 5% を受け取る／ID は重複不可／貸付は資金の範囲内／入金は必ず銀行経由
