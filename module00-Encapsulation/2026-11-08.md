# Module 00 - Encapsulation / S5: operator[] をメンバ関数に・static と map の理解（2026-11-08）

## やったこと

- `createAccount` を `clientAccounts[new_id] = new Account(new_id, value); new_id++;` にした

## 疑問→理解のラリー

### なぜ operator[] に friend が要らないのか
- 疑問: `operator[]` はクラス外にある演算子をオーバーロードするものだから、`operator<<` と同じく friend で private を読ませる必要があると思っていた
- 理解: `operator[]` もオーバーロードには違いない。違いは「メンバ関数で書くか、クラス外の自由関数で書くか」
  - `operator<<` は左オペランドが `std::ostream` で、ostream はいじれないから自由関数にするしかない → private を読むために friend
  - `operator[]` は左オペランドが `Bank` 自身。`bank[0]` は `bank.operator[](0)` にしか展開されない。メンバなので `this` があり、private に最初から触れる
  - friend を付けると「非メンバ」になり `this` が消える。`clientAccounts` が何を指すか分からなくなるし、非メンバに `const` 修飾は付けられない。**friend は不要というより、付けると壊れる**

### static とは
- 疑問: 「非 static メンバでなければならない」の意味が分からない。static 自体を忘れていた
- 理解: クラス内の `static` は「オブジェクトではなくクラスに属する」。インスタンス間で共通のメモリを1つだけ持つ
  - 非 static メンバ関数は呼び出し元オブジェクトを `this` として隠し引数で受け取る。`a.deposit(0, 100)` は実質 `deposit(&a, 0, 100)`
  - static メンバ関数は `this` を受け取らない。「どのインスタンスの liquidity か」の情報が無いので非 static メンバ変数には触れない。static メンバだけ扱える
  - 逆（非 static 関数から static 変数を読む）は普通にできる
  - 関数内ローカルやファイルスコープの `static` は別の意味（寿命・リンケージ）。今回は無関係

### なぜ `=` `[]` `()` `->` の4つはメンバ限定なのか
- 疑問: 自由関数 `operator[](Bank&, size_t)` でも左側を引数で受け取れるはず。`operator+` はそれが許されているのに、なぜ `[]` は禁止なのか
- 理解（1回目の誤解）: 「int などの primitive 型に対して演算子が定義できてしまい意味が怪しくなるのを防ぐため」と思った
  - 訂正: 演算子オーバーロードは「オペランドの少なくとも1つがクラス型か enum」でないと候補にならない。`operator+(int, int)` はそもそも書けないので、primitive 型はこの制限とは別のルールで既に守られている
- 理解（本質）: **自由関数の演算子は左オペランドにも暗黙変換がかかる。メンバ関数の `this` 側には暗黙変換がかからない**。この非対称性が核
  - 例: `Bank → Account` の暗黙変換があり、自由関数 `operator[](const Account&, size_t)` が許されていたら、`bank[0] = 100;` は「bank を一時的な Account に変換し、その一時オブジェクトを `[]` する」になる。100 は文末で消える一時物に書かれ、bank には何も起きない
  - `=` も同じで、`bank = x;` が「変換で生まれた一時物への代入」になり結果が黙って捨てられる
  - 「オブジェクトそのものを書き換える」のが仕事の演算子で、操作対象がソースに書いた `bank` ではない別物にすり替わるのは致命的。メンバ限定にすれば `this` は必ず `bank` 自身
  - 一時オブジェクトを触ること自体が悪いのではない（`Bank().deposit(0, 100)` は合法）。「書いた人は bank を触ったつもりなのに、実は別物だった」という**意図とのズレが黙って起きる**のを排除したかった
  - 4つの内訳: `=` は対象を書き換える（コピー代入はコンパイラがメンバとして暗黙生成するので自由関数版と共存すると混乱）、`[]` は中身への参照を返す（一時物ならダングリング）、`()` は関数オブジェクトの呼び出し、`->` はスマートポインタ
  - `+` や `<<` は「2つの値から新しい値を作る」演算子。左が一時物でも害がなく、左が `ostream` や `int` のケースのために自由関数を許す必要があった
  - 余談: C++23 で `operator()` と `operator[]` だけ static が許された（状態を持たない関数オブジェクト向け）。C++98 では無関係

### std::map の find はイテレータを返す
- 疑問: value を取り出すのは `map.find(key)` でいいのか
- 理解: `find` は値ではなく**イテレータ**を返す。値は `it->second`（`it->first` が key）。見つからないと `end()` が返るので判定が必要
  - `*it->second` で `Account*` を参照外しして `Account&` に
  - `clientAccounts[id]` は「無ければデフォルト値を挿入してから返す」。`Account*` なら `NULL` が挿入され、`->value` で落ちる。存在確認したい場面は `find`
  - `deleteAccount` の `Account* account = clientAccounts.find(id);` も同じ誤り（イテレータをポインタに入れようとしている）

### const 関数から非 const の `Account&` を返していた
- 疑問: `Account& operator[](size_t) const` がコンパイルは通るのに何が問題か
- 理解: map が持っているのは `Account*` というポインタ。const が付くのは「ポインタの値」だけで指し先には付かない。`const Bank&` を受け取った側が口座の中身を書き換えられるカプセル化の穴
  - const 版は `const Account&` を返す。`operator<<` は `const Bank&` から呼ぶのでこちらを使う
  - `deposit` などから書き換え用に使うなら非 const 版 `Account& operator[](size_t)` を別に用意する（定石の2本立て）
  - イテレータ自身への `const`（`const Accounts::const_iterator it`）は害は無いが `++it` できなくなるだけなので普通は付けない

### `#define` ではなく `typedef`
- 疑問: `#define Accounts std::map<size_t, Account *>` で何が悪いか
- 理解: マクロはスコープを無視して置換する。`Account` が解決できるのは「たまたま Bank の中で使われているから」。クラス内 `typedef` なら意図が明確でファイル全体を汚さない

### map に insert が無いと言われる
- 疑問: `clientAccounts.insert(new Account(new_id, value))` が「no matching function」になる
- 理解: 「insert が無い」ではなく「`Account*` を1つだけ受け取る insert が無い」。map の要素型は `std::pair<const size_t, Account*>` で、どの key に紐付けるかを必ず一緒に渡す
  - A: `clientAccounts.insert(std::make_pair(new_id, new Account(new_id, value)));`（同じ key があると挿入されず戻り値 `.second` が false）
  - B: `clientAccounts[new_id] = new Account(new_id, value);`（短い。無い key なら作ってから代入する性質を利用）
  - `new_id` は重複しないのでどちらでもよい。B を採用

### 後置インクリメントを同じ式に混ぜられない
- 疑問: `clientAccounts[new_id++] = new Account(new_id, value);` が `-Werror=sequence-point` で弾かれる
- 理解: 後置インクリメントが禁止なのではなく、**同じ式の中で `new_id` を書き換えつつ別の場所でも読んでいる**のが問題
  - C++98 では代入 `=` の左辺と右辺の評価順が決まっていない。右辺の `new_id` がインクリメント前か後か不定 → key と id が食い違いうる（未定義動作）
  - C++17 で「代入は右辺を先に評価」と決まったが、C++98 では未定義のまま。読む人も混乱するので避ける
  - 一般則: 「同じ変数を1つの式の中で2回以上触り、1回以上が書き換えなら怪しい」。`i = i++`、`a[i] = i++` と同じ仲間
  - 直し: 2行に分ける（`clientAccounts[new_id] = ...; new_id++;`）

## 残っているコンパイルエラー（`-Wall -Wextra -Werror -std=c++98`）
1. `deleteAccount`: `find` はイテレータ。`it->second` を `delete` してから `clientAccounts.erase(it)` で map からも外す
2. `Bank()` と `~Bank()` が `public:` より前にあり private 扱い。main で `Bank bank` が作れない → `public:` 以下へ移す
3. main の `bank.liquidity` が private で弾かれる（S3 の確認用なら残す、動かすなら消す）

## エラーではないが直す箇所
- コンストラクタで `new_id` を初期化していない（最初の id がゴミになる）
- デストラクタと `operator<<` の `for (i < size())` は id が連番で欠けていない前提。削除後に崩れる。デストラクタ内の `clientAccounts[i]` は存在しない id だと `NULL` を map に挿入する → `begin()` から `end()` までイテレータで回す
