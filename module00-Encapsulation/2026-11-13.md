## loan と repay で決めた要件とその根拠

### 返済も実装する
- 課題文4ページの "everybody can get them without having to do anything, or even having to pay them back!" は、元のコードの**欠陥**として書かれている。「返さなくていい」という仕様ではない
- 要件の箇条書き（5ページ）にあるのは「資金の範囲内で融資できる」だけ。返済は必須ではない
- それでも、4ページで「返さなくていいのはおかしい」と言っている以上、評価で聞かれる可能性がある。だから作る

### 借りている額は `Account` の属性として持つ
- 返済するには、口座ごとに「いくら借りているか」を覚えておく必要がある
- 書き換えるのは friend の `Bank` だけ。`Account` にメソッドは増えないので、ボーナス条件（`Account` には const getter だけ）に反しない

### 融資の手数料は、借りた額から 5% を引く（天引き）
- 100 借りると口座には 95 入り、返すのは 100
- 根拠: 要件は "The bank must receive 5% of each money inflow on these client accounts"。融資も口座へのお金の流入なので、5% を取らないと「要件に従っていない」と言われたときに反論できない
- 流入した 100 から 5 を取る形が、要件の文面に一番素直に合う
- 検討した別案: 100 を満額渡し、手数料 5 は口座の手持ちから払う
  - 数値の結果は天引きと同じ（口座 +95、銀行 −95、借金 100）。違いは「残高 0 の口座が借りられるか」だけ
  - 「流入とは別に手持ちから取る」理由の説明が一段増えるのでやめた
- 現実の銀行の主な取り分は利息（借りた期間で増える額）。融資の手数料は、天引き・別払い・手数料込みで借りる、のどれも実在する
- 利息は時間の概念が必要になり、課題の範囲を超えるので入れない

### 借金額は `amount`（100）で記録する
- `credited`（95）で記録すると、返済で 95 しか戻らず、銀行の収支が 0 になる。手数料を取った意味がなくなる

### 融資で銀行の資金を減らす
- `liquidity -= credited`（貸した 100 を出し、手数料 5 を受け取る。差し引き −95）
- 最初は `liquidity += fee` しか書いておらず、銀行の資金を使わずに無からお金を作っていた

### 「資金の範囲内で」の検査
- `amount > liquidity` なら `InsufficientLiquidity`。必須要件そのもの
- 資金は減る一方なので、`loan` では銀行側の `INT_MAX` 検査は要らない
- 口座側は2つ検査する: 残高（`credited > INT_MAX - value`）と借金額（`amount > INT_MAX - loan`）

### 返済の検査と更新
- 検査: 金額が正か → 口座があるか → 借りている額を超えていないか → 残高が足りるか → 銀行の資金があふれないか
- 返済は口座からお金が出ていく側なので、手数料は取らない
- 検査を全部終えてから、3つ（銀行の資金 +、借金額 −、残高 −）をまとめて更新する。途中で例外が出たときに、一部だけ変わった状態を残さないため

### 足りないときの例外は、原因でクラスを分ける
- 足りなくなる場面は3つ、原因は2種類
  - `withdraw` / `repay`: **口座**の残高が足りない → `InsufficientFunds`（文面から "withdrawal" を外して汎用にした）
  - `loan`: **銀行**の資金が足りない → `InsufficientLiquidity`
- 根拠: 受け取る側が型で見分けられる。客にとって「残高不足」は自分で入金すれば解決するが、「銀行の資金不足」は自分ではどうにもならない
- S9 で `overflow_error` の文面を「銀行の上限」と「口座の上限」に分けたのと同じ考え方
- 不採用: コンストラクタで文面を受け取る形（`InsufficientFunds(const std::string&)`）。`catch` する側が文面を読まないと区別できない

### 検査の順番のルール
1. **依頼が成り立っているか**（金額が正か、口座が存在するか）
2. **今それに応じられるか**（資金・残高・上限）
- 最初は `loan` で資金の検査を `getAccount` より前に置いた。「口座を探す前に終われるのでパフォーマンスがいい」と考えた
  - しかし `map::find` は O(log n)（口座 100 万でも比較 20 回程度）で、しかも短くなるのは失敗するときだけ。差はほぼない
- 決め手は「誤りの深さ」
  - 口座がない: 依頼そのものが間違っている。何度やり直しても成功しない
  - 資金不足: 依頼は正しいが、今は応じられない。入金が増えれば成功する
  - 存在しない ID に「資金不足」と返すと、呼び出し側は「待てば借りられる」と受け取り、ID の誤りに気づけない
- `deposit` / `withdraw` / `repay` はもともとこの順番。`loan` も合わせたので、全メソッドを同じルールで説明できる

### getter について
- `loan` / `repay` は口座を**変える**メソッドで、getter は口座を**読む**メソッド。片方があってももう片方の代わりにはならない
- getter がないと、テストで数値（残高 95 など）を確かめられない。`operator[]` が返す `const Account&` からも何も読めない
- 必須要件「意味がある箇所には getter」にも当たる（客が自分の残高や借金額を確認するのは意味がある）
- 決めたこと: getter はテストで必要になったときに書く
- setter は作らない。値を変えるのは `deposit` / `withdraw` / `loan` / `repay` の役目で、setter は「意味がない」側に入る

## テストの設計で考えたことと決まったこと

### 疑問: `{クラス名}_test` という作り方に名前はあるか
- 作り方そのものに決まった名前はないが、ごく一般的な慣習
  - **単体テスト（unit test）**: クラスや関数を1つずつ確かめるテスト
  - テストファイルを対象と1対1で置く（Google Test の `bank_test.cpp`、Go の `bank_test.go`、Python の `test_bank.py`）
  - **xUnit**: JUnit・Google Test などのテストフレームワーク系統の総称。「テスト関数を並べる → 1つずつ実行 → 期待値と比べる → 結果を集計」
  - **Arrange-Act-Assert（AAA）**: テスト関数1つの中身の書き方。準備（口座を作る）→ 実行（`loan`）→ 確認（残高が 95 か）

### 疑問: ヘッダを作って `main` から呼ぶのは一般的ではないのか
- Google Test・Go・pytest では、**テストランナー**（テストを探して実行する仕組み）がテスト関数を見つけて呼ぶ。だからヘッダも、提出用の `main` からの呼び出しも出てこない
- 今回は外部ライブラリが禁止で、テストランナーがない。「テストを集めて呼ぶ」役を自分で書く必要がある
- その役を `main` が担い、呼ぶためにヘッダで宣言する。ライブラリなしでやる場合の自然な形
- （Claude が最初に「一般的なやり方と違う」と書いたのは、テストランナーがある前提での一般化だった）

### 決まったこと
- `Bank_test.hpp` で `runBankTests()` を宣言し、`Bank_test.cpp` に中身を書く
- テストは public なインターフェース（メソッドと getter）だけを使う。`friend` にして中身を覗くと、「外から触れない」ことの確認にならない
- 中身は AAA の形で書き、自前の `check(条件, "テスト名")` 関数で結果を出す（xUnit の作りを手書きする）
- `Account` 単体のテストは作らない（S9 で決めた。振る舞いがすべて `Bank` 経由なので）
- `main` はデモ兼テストランナーにする
  - **デモ**: 銀行の動きを見せる。内側の `try` / `catch` で `Bank` の例外を受けて表示し、続けて動く（ボーナス要件「main がエラーを受ける」を見せる場所）
  - **テスト**: `runBankTests()` を呼ぶ。期待どおりに例外が出るかは、テスト関数の中で `catch` して確かめる。`main` までは届かせない
  - **外側の `try` / `catch`**: 想定外の例外（`bad_alloc` など）を受けて、落ちずに終わる（共通ルール「どんな状況でも落ちない」）
- テストだけにしなかった理由: 評価で「銀行の動きを見せるデモ」がない状態になる
