# 42 の学習メモの書き方

このリポジトリのメモは、ユーザーが後で読み返して「何を考えて、どう理解したか」を思い出すためのもの。
評価（defense）で自分の言葉で説明できるようにするのが最終目的。
だから、正しい説明がきれいに並んでいることより、**ユーザー自身の言葉と思考の道筋が残っていること**が大事。

## 書く前に

1. **頼まれたときだけ書く**。メモもコードも、ユーザーが自分で書くのが基本。頼まれていないのに作らない。
2. **対象のファイルを読み直す**。ユーザーは会話の途中でメモを自分で編集する。見出しや文が変わっていたら、それが今の正しい状態。元に戻さない。
3. **同じ module の直近のメモを 1 つ読む**。見出しの名前と文体をそろえるため。

## ファイルとタイトル

- 場所: `moduleXX-Name/YYYY-MM-DD.md`（その日のファイルがあれば追記、なければ新規）
- タイトル: `# Module XX - Name / S番号: その日の要約（YYYY-MM-DD）`
  - S 番号は module ごとの通し番号。直近のメモの番号 + 1。module の最初は S1
  - 要約は「・」で区切って、やったことや分かったことを短く並べる
- 例: `# Module 01 - Relationship / S1: subject を読んだ・3 つの関係の見分け方（2026-11-23）`

## 見出し

内容に合うものだけを使う。空の見出しは作らない。過去のメモで使ってきた名前:

- 課題文を読んだ日: `## 提出物` `## 禁止事項` `## 評価の観点`
- 実装した日: `## やったこと` `## 決めたこととその根拠` `## 学んだこと` `## 次の15分`
- 概念を理解した日: `## 疑問に思ったことと、その答え`（下の形式）

## 原則 1: ユーザーの言語化を土台にして、直した形で書く

ユーザーが自分の理解を言葉にしていたら、その文をそのまま土台にする。
間違いや不足は、**文の中身を直して**反映する。指摘として横に書かない。

理由: 「〜ではない」「〜も足す」という指摘は、会話の中でしか意味を持たない。
読み返したときに欲しいのは「結局どうなのか」が自分の言葉で書いてある文。指摘を読んでも内容は思い出せない。

悪い例（言語化への指摘になっている）:
```
- **ログは課題文が求めている**（「いいかも」ではない）。ほぼすべての関数に出力を入れる
```

良い例（ユーザーの文を直してある）:
```
アーキテクチャやコード設計が評価の対象なので、どのような処理がどのような順序で行われているかが
プログラムの出力から説明できるように、ほぼすべての関数・コンストラクタ・デストラクタにログを組み込む（課題文の指定）。
```

足す情報は、ユーザーの文と同じ調子の文として続ける。箇条書きの見出し語を新しく作って並べ直さない。

## 原則 2: 疑問は、思考の道筋ごと残す

会話でユーザーが疑問を出して理解していった内容は、疑問 1 つにつき次の 4 つをセットにする。

```
### 疑問 N: （ユーザーが聞いたこと。ユーザーの言い方に近く）
最初の理解: （聞いた時点でユーザーが考えていたこと）

答え: （結論を 1 文。そのあとに根拠を箇条書き）

最後の自分の言語化:
> （理解したあとにユーザーが言った文を、ほぼそのまま引用）
```

- 「最初の理解」と「最後の自分の言語化」は、ユーザーの発言から取る。言い換えてきれいにしない。本人の言い回しのほうが思い出す手がかりになる
- 最後の言語化に補足が必要なら、引用の下に括弧で 1 行だけ足す
- その疑問に確認の発言がなかったら、次の疑問につながった発言を入れて、`（しっくりこないまま疑問 N+1 に続く）` のように書く。作文しない
- 疑問は出た順に並べる。前の答えから次の疑問が生まれた流れが読めるようにする
- 違和感が正しかったときは「この違和感は正しい」と書く。あいまいさが残る話（設計者の選択で決まる、など）は、あいまいなまま書く

疑問が複数あって全体の結論や判断の手順が出たときは、疑問の節の前にまとめて置く（結論、判断の順番、比較の表）。

## 原則 3: 頼まれた範囲だけ書く

- 頼まれた内容だけを入れる。同じ日に話した別の話題（例: relink の理由）は、頼まれなければ入れない
- 役に立ちそうな節（例: 「評価での答え方」）を自分の判断で足さない。足したいときは、書かずに提案する
- 頼まれていない変更をした場合（タイトルの書き換えなど）は、報告で必ず伝える
- 報告では「入れたもの」と「入れなかったもの」の両方を短く言う

## 原則 4: 課題文を写さない

README の決まり: 課題文は公開しない。メモには自分の言葉で書いたものだけを置く。
- 要件は自分の言葉で書く。課題文の段落を貼らない
- 根拠として示すときは、短い語句の引用にとどめる（例: "neither object is dependent on the other"）
- 課題文とユーザーの理解が食い違ったら、課題文の内容に合わせて文を直す（原則 1）

## 文体

- 日本語。「だ・である」か体言止め。1 文を短く
- クラス名・ファイル名・コマンドはバッククォート
- 3 つ以上を同じ観点で比べるときは表
- 課題の具体例を付ける（`Worker` と `Shovel` のように、この課題のクラスで言う）
- 評価でそのまま言える 1 文があれば、引用（`>`）で置く

## 書いたあと

報告は短く: どのファイルのどこに何を足したか、判断に迷って決めたこと、入れなかったもの。
メモの全文を返信に貼らない。
