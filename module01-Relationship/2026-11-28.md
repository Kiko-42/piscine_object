# Module 01 - Relationship / S6: `giveTool()` と `use()` を書いた・関数の定義を `.cpp` に移した（ODR）・継承の種類は「外から基底クラスとして扱えるか」を決める・`protected` は自分と派生クラスだけ（2026-11-28）

## やったこと
- `Shovel.hpp` に書いていた `use()` の定義に warning が出たので、`Shovel.cpp` に移した。`Hammer.hpp` / `Hammer.cpp` も同じ形で作った
- `Worker.cpp` に `giveTool()` を書いた。最初は `push_back` して `user` を書き換えるだけだった
- レビューを受けて直した
  - `giveTool()` で、前の持ち主の `tools` から道具を消すようにした（`std::remove` と `erase`）
  - `numberOfUses` を `Shovel` と `Hammer` から `Tool` に移し、`protected` にした。`Tool()` の初期化リストで 0 にした
  - `Tool()` と `~Tool()` に定義を書いた（宣言だけでリンクエラーになっていた）
  - `std::vector<Tool *>` に `Tools` という名前を付けた（`typedef`）
- まだコンパイルは通らない。残っているのは次の 3 つ
  - `Shovel` と `Hammer` が private 継承のまま（`'Tool' is an inaccessible base of 'Shovel'`）
  - `user` を `protected` にしたので、`Worker::giveTool` から `tool->user` に触れない（`'Worker* Tool::user' is protected within this context`）
  - `user` が初期化されていない。ごみ値だと `giveTool()` の「前の持ち主がいるか」の判定が正しく動かない

## 学んだこと

### 定義をどこに書くか（ODR）
- ODR は One Definition Rule。同じ関数の定義はプログラム全体で 1 つだけ、という規則
- `#include` はヘッダの中身を `.cpp` に貼り付ける。class の外に書いた関数の定義がヘッダにあると、include した `.cpp` の数だけ定義ができる
- include する `.cpp` が 1 つの間は動く。2 つになると `multiple definition` のリンクエラーになる

| 種類 | ヘッダに定義 | 理由 |
|---|---|---|
| 普通の関数（class の外） | ✗ | 定義が複数できる |
| template の関数・class | ○ | ODR の例外 |
| `inline` を付けた関数 | ○ | ODR の例外 |
| class の `{ }` の中に書いた関数 | ○ | 自動で `inline` 扱い |

### `giveTool()` の要件
- 課題文は、すでに渡されている道具を別の `Worker` に渡したら、最初の `Worker` から外すことを求めている
- 前の持ち主から消す処理を入れると、同じ `Worker` に同じ道具を 2 回渡して `tools` に 2 個入る問題も一緒に消える
- `std::remove` は消したい要素を後ろに寄せるだけ。実際に縮めるのは `erase`
- `tool->user->tools` は private だが、同じ class の別のオブジェクトなので `Worker` のメンバ関数から触れる

### アクセス指定と継承の種類は別の仕組み

メンバのアクセス指定は、基底クラスのメンバを誰が触れるかを決める。

| 基底クラスでの指定 | 基底クラス自身 | 派生クラス | 外（`main` など） |
|---|---|---|---|
| `public` | ○ | ○ | ○ |
| `protected` | ○ | ○ | ✗ |
| `private` | ○ | ✗ | ✗ |

継承の種類は、基底から受け継いだメンバが派生クラスの中でどの指定になるかを決める。

| 基底での指定 | `public` 継承 | `protected` 継承 | `private` 継承 |
|---|---|---|---|
| `public` | `public` | `protected` | `private` |
| `protected` | `protected` | `protected` | `private` |
| `private` | 見えない | 見えない | 見えない |

| 決めたいこと | 使う仕組み |
|---|---|
| どのメンバを外に見せるか | 基底クラスの中の `public` / `protected` / `private` |
| 派生クラスを基底クラスとして扱わせるか | 継承の種類 |

> 継承の種類が決めるのは、派生クラスが基底の何を見られるかではなく、外から見て派生クラスを基底クラスとして扱えるか。

## 議論の要約（疑問に思ったことと、その答え）

### 疑問 1: `Shovel.hpp` の `use()` に warning が出ている。ODR violations ってなんだ
最初の理解: （なし。warning の意味が分からなかった）

答え: class の外に書いた関数の定義がヘッダにあるため。ODR は「同じ関数の定義はプログラム全体で 1 つだけ」という規則。
- 2 つの `.cpp` が `Shovel.hpp` を include すると、`Shovel::use()` の定義が 2 つできる
- 直し方は 3 つ。`Shovel.cpp` に移す・`inline` を付ける・class の `{ }` の中に書く。`Shovel.cpp` に移した
- template はヘッダに定義を書いてよい。template はそれ自体がコードではなく、`Foo<int>` のように使われた時点でコンパイラがコードを作る。作るには定義の中身が見えている必要があるので、ODR の例外になっている

最後の自分の言語化:
> ああ、templateの定義と混同していたようです

### 疑問 2: class の継承は何も書かないと private になり、`Shovel *` を `Tool *` に変換できない。これってどういう考え方なんだっけ
最初の理解: private継承とpublic継承の違いは派生クラスが基底クラスのprivateを見れるか見れないかの違いしかないと思っていた

答え: 継承の種類が変えるのは、外から見て派生クラスを基底クラスとして扱えるかどうか。
- 基底の `private` は、どの継承でも派生クラスから見えない
- 継承の種類は、受け継いだものを外にどこまで見せるかの上限
- private 継承では「`Shovel` が `Tool` を継承している」という事実そのものが `Shovel` の private な情報になる。`main` はその事実を知らない扱いなので、変換できない
- `Shovel` 自身のメンバ関数の中なら、変換もアクセスもできる

（しっくりこないまま疑問 4 に続く）

### 疑問 3: `protected` ってなんだっけ
最初の理解: publicとprivateの間の概念というのは覚えているんだけど、基底クラス、派生クラスでの扱いを忘れた

答え: 自分と派生クラスだけが触れる。外（`main` など）からは触れない。
- `numberOfUses` を `Tool` の `protected` に置くと、`Shovel::use()` と `Hammer::use()` からは増やせて、`main` からは触れない

（確認の発言なし）

### 疑問 4: 継承の種類について、まだピンときていない
最初の理解: private継承だと、基底クラスのpublicの要素もprivate扱いになる -> 基底クラスのconstructorもprivateになる -> 外から基底クラスを継承しているとわからない みたいな判定なのか？

答え: constructor は関係ない。「継承している」という関係そのものにアクセス指定が付き、変換できるかはその指定で直接決まる。
- 連鎖ではなく、「`Shovel` の中にある `Tool` の部分が private」という 1 つのことから、2 つの結果が並んで出る
  - `Tool` の public メンバが、`Shovel` 経由では private 扱いになる
  - `Shovel *` から `Tool *` への変換が、`Shovel` の外ではできなくなる
- 変換できる場所の判定は、「その場所で、`Shovel` 経由で `Tool` の public メンバに触れるか」と同じ
- 継承の種類は `Tool` 自身の constructor のアクセス指定を変えない。`Tool` の constructor を呼ぶのは `Shovel` の constructor で、`Shovel` の中からなので、どの継承でも呼べる
- private 継承は、`Tool` の部分を private なメンバ変数（`Tool base;`）として持つのに近い。`main` から `s.base` に触れないので `s.base.user` にも触れず、`&s.base` も取れないので `Tool *` を得られない

最後の自分の言語化:
> なるほど？今回で言うと、userもToolの要素だから、mainからShovel sのs.base.userにアクセスできないって感じか

（この理解で合っている）

### 疑問 5: `main` から `Shovel` の `user` に直接アクセスしたいことってあるんだろうか
最初の理解: use()のときにoldユーザーからはずす　みたいな、適切な抽象化をすべきで、Toolクラスに直接アクセスされるのはできる限り防ぐほうがよいとう考えだった

答え: `user` を外から触らせないという目的は正しい。それを実現する手段は継承の種類ではなく、`Tool` の中のアクセス指定。
- private 継承は `user` だけでなく、「`Shovel` は `Tool` である」という関係ごと隠す。この関係は `giveTool(&shovel)` と `Tools` に必要なので、隠してはいけない
- private 継承では `user` を守り切れない。`Tool` で public のままなら、`Tool *` を持っている場所から書き換えられる
- 前の持ち主から外すのは `giveTool()` のとき。`use()` は使用回数を増やすだけで、持ち主は変えない
- 目的に合う書き方として、`Tool` の中で `user` を `private` にし、`friend class Worker;` で `Worker` だけに触ることを許す形が出た

最後の発言:
> 複雑になってきた
> Tool の中で user を private にし、Worker だけに触ることを許す
> の理解は次回にします。

（`friend` の部分は理解していないまま次回に持ち越し）
