## 議論で理解できたこと

### C++ の仕組み
- `= 0` は数値の代入ではなく、「この関数は純粋仮想関数」という印の構文。アドレスの 0 とは関係ない
- プログラムが扱うアドレスは、そのプロセス専用の仮想アドレス空間の中のもの。0 番地は「自分の空間の中にある、何も割り当てられていない場所」
- 関数は、コード領域に命令そのものが順番に並んだもの。関数の名前は先頭の命令のアドレス。「アドレスが格納されている表」は関数の中ではなく vtable のほうにある

### 設計の判断（`Tool` の持ち主をどう持つか）
- 「アドレスで持ち主を探す」案（B）には、全 `Worker` を知っている誰かが必要になる
- 判断の基準は、現実に似ているかではなく、「誰が誰を知っている必要があるか」と「同じ事実を何か所に持つか」
- 二重管理は弱点だが、ナンセンスではない。条件は、更新する場所が 1 つに決まっていること
- public な操作は、どれを呼んでも両側がそろった状態で終わるようにする。隠す必要があるのは、片側だけを更新する操作
- 「今はシンプルにして、条件が変わったら設計を変える」は YAGNI。大事なのは将来の形を当てることではなく、変えるときに直す場所を少なくしておくこと

### 依存の考え方
- 関係の種類（寿命と所有）と、依存の向き（誰が誰を知っているか）は別の軸。aggregation はむしろ「`Tool` は単体で存在する」側の関係
- 「知っている」には段階がある。ポインタを持つだけ（名前だけ知っている）は弱い依存、相手のメソッドを呼ぶのは強い依存
- 強い依存を避けるのは、依存先が変わると依存している側も直す必要が出るから。両方向になると、2 つのクラスが実質 1 つのかたまりになる
- これらの原則は「禁止」ではなく「代償がある」。代償は規模・寿命・人数に比例するので、42 の 1 課題では軽い

## 決めたこととその根拠

`Tool` に持ち主のポインタを持たせる（A）。更新の本体は `Worker::giveTool` に置く。

`Tool` に所有者のポインタを持たせることは、`Worker` が `Tool` のポインタを持つこともあり、情報の二重管理になってしまう。これは single source of truth に反しており、片方を更新したときにもう片方を更新し忘れるリスクがあったり、機能修正時にはそれを考慮する必要があるため脳への負荷が上がることになる。
二重管理への対処として、1 つの関数内で更新を済ませられるようにすることで、操作をシンプルにし、リスクを低くすることは可能。そのためには、片側だけを更新する操作（持ち主だけを書き換える・`tools` に足すだけ）を public にしない。

一方で、`Tool` に所有者情報を持たせず、二重管理を避ける選択肢もある（B）。
これを選んだ場合、誰かが持っている道具を別の `Worker` に渡すときには、その道具をどの `Worker` が持っているのかを調べるために、`Worker` に static の `Worker` リストを持たせて constructor / destructor で insert / remove をすることが必要となり、`Worker` が若干責務を超える。または `Workers` というオブジェクトを 1 つ増やすことになる。

現状の機能仕様を考えると、二重管理に対しては 1 つの関数で管理可能ということもあり、オブジェクトを増やしたり `Worker` の責務を増やしたりするより実装がシンプルになるため、二重管理のほうがマシという判断になる。

テストの観点でも、更新の本体を `Worker` 側に置けば、`Tool` は `Worker` の名前しか知らず（ポインタを持つだけの弱い依存）、`Shovel::use` などを `Worker` なしでテストできる状況を維持できるので問題にならない。`Worker` から `Tool` は `use()` を呼ぶ強い依存だが、道具を使うのは `Worker` の本来の役割なので問題のない依存。

持ち主になれる相手が `Worker` 以外に増えたら、その関数の中を作り直す。

| 案 | 持ち主の調べ方 | 利点 | 代償 |
|---|---|---|---|
| A（採用） | `Tool` が持ち主のポインタを持つ | 道具から 1 手で持ち主に届く。全体のリストが要らない | 同じ事実が 2 か所にある。`Tool` も `Worker` を知る |
| B | 全 `Worker` のリストから、道具のアドレスで探す | `Tool` が `Worker` を知らない。記録は `tools` の 1 か所だけ | プログラム全体で共有されるリストが要る。渡すたびに全員を調べる |

> 双方向にした代償は二重管理。更新を 1 つの関数に閉じ込めたので、持ち主の種類が増えたらその関数の中を作り直す。

よく持ち出される説明の名前:
- 「X は Y を知らなくていいはず」のほう: 結合度（低く保つ）・循環依存（非循環依存関係の原則）・情報隠蔽
- 「同じ事実を 2 か所に持つ」のほう: Single Source of Truth / DRY
- 今回の形そのもの: Fowler『リファクタリング』の「双方向の関連を単方向にする」

## 議論の要約（疑問に思ったことと、その答え）

### 疑問 1: `= 0` はなんで 0 を入れるんだっけ
最初の理解: virtual だけだと `Tool.use` も call しちゃうからか。そこで定義がないままだとコンパイラに怒られそうだし、明示的に 0 をいれているんだっけ。関数ってアドレスを指しているはずだから、0 を指すと 0x00 を指すよね。いいの？

答え: `= 0` はアドレスの 0 ではない。「純粋仮想関数です」という印の構文。
- キーワード（`pure` や `abstract`）を増やさずに済ませるために選ばれた書き方。`= 1` や `= NULL` はコンパイルエラー
- 予想の後半（定義がないと怒られる）が近い。`virtual void use();` だけだと「本体がどこかにある」という約束になり、本体がないとリンク時に undefined reference になる。怒るのはコンパイラではなくリンカ
- `= 0` があると `Tool` の実体を作れないので、「`Tool` そのもの」に対して `use()` が呼ばれる場面がなくなる
- `Tool` の vtable の `use` の欄は 0 ではない。GCC と Clang では `__cxa_pure_virtual` が入る（万一呼ばれると異常終了する）。これは実装の話で、規格は vtable 自体を定めていない

最後の自分の言語化:
> なるほど。= 0は数値の代入ではなく、構文として特別な意味を持たせているのか.
> コンパイラがvirtualかつ= 0を認識してpure やabstructのような解釈をして、vtableに__cxa_pure_virtualを入れるイメージ？

（このイメージで合っている）

### 疑問 2: プログラム上で 0x00 ってやると OS 空間全体に対して干渉できるんだっけ
最初の理解: 仮想的なプログラム領域が作られて、その領域内でのアドレスを操作するイメージを持っていた。

答え: このイメージが正しい。0x00 に触っても、OS や他のプロセスのメモリには届かない。
- OS は各プロセスの仮想アドレス空間で、0 番地の付近をわざと何も割り当てないままにする
- 割り当てのない場所に触ると、OS がそのプロセスに SIGSEGV を送る（segmentation fault）
- アドレス 0 はスタック領域ではない

（確認の発言なし）

### 疑問 3: 関数ってどんなメモリ表現になるの
最初の理解: `void use()` がアドレス 0xa1 を指していて、0xa1 からのメモリに関数内の処理一つ一つが格納されるアドレスが格納されているイメージ。

答え: 1 段多い。0xa1 からのメモリには、処理そのもの（機械語の命令）が直接、順番に並んでいる。
- 置かれるのはコード領域（text）。読み取りと実行だけができる
- 関数の名前は先頭の命令のアドレス。呼び出しは「戻り先をスタックに積んで、先頭にジャンプする」
- メンバ関数も同じ。命令の列はクラスに 1 つだけで、どのオブジェクトかは隠れた引数 `this` で渡される
- vtable は「関数の先頭アドレスを並べた配列」

（確認の発言なし）

### 疑問 4: `Tool` が持ち主の情報を保持しているのはおかしい気がする
最初の理解: 現実世界で考えたとき、確かに shovel に名前を書くことは可能ではあるが、ピュアなオブジェクトとしての shovel にはそんな特性はない。shovel のアドレスで捜査して、同じアドレスの shovel を所有していることになっている `Worker` を所有者とするほうが健全というか、現実世界にあっているのではないか。

答え: その案（B）には、全 `Worker` を知っている誰かが必要。`workerB` は `workerA` の存在を知らない。
- 課題文が求めるのは「別の worker に渡したら、最初の worker から外れること」だけ。方法は指定されていない
- 違和感のうち正しい部分: A は同じ事実を 2 か所に持つ。「`Tool` は `Worker` を知らなくていいはず」という依存の向きの感覚も筋が通っている
- 基準にしにくい部分: 「現実の shovel に持ち主の情報はない」。現実でも、今誰が持っているかを知るには全員に聞いて回る必要がある

最後の自分の言語化:
> あーたしかに...それならtoolにworkerへのポインタを持たせたほうが、設計としてシンプルだ

答え: ある。上の「よく持ち出される説明の名前」のとおり。どれも「禁止」ではなく「代償がある」という原則。

### 疑問 6: `Worker` からも take できる必要があるなら、B が選択肢に入ってくるか
最初の理解: 今回は worker が tool を take することは不可能であるという要件だから、tool クラス内で worker の操作も完結する。両側から操作できる必要があるなら、tool にも worker にも整合性を保つための関数を作らないといけなくなるから、B も選択肢に入ってくる。

答え: 半分合っている。
- そういう要件はない。課題文が求めるのは、渡せること・取り上げられること（返せること）・別の worker に渡したら元の worker から外れること。誰のメソッドで行うかは設計者の選択
- 入口が 2 つあることと、更新する場所が 2 つあることは別。片方が本体を持ち、もう片方はそれを呼ぶだけにできる
- B が選択肢に入ってくるのは、`Tool` を `Worker` なしで使いたい・持ち主になれる相手が増える・更新を 1 つの関数に閉じ込められなくなる、のどれかのとき

### 疑問 7: aggregation だから、`Tool` を単体テスト状態にすることにはあまり価値がない、という考え方でいいか
最初の理解: 「単体で使える・テストできる」は前職でかなり重要視されていたが、理解が浅く「そういうもの」として考えてしまっていた。今回は aggregation だから価値がなく、B はそこまで重要じゃない。

答え: 結論（今回 B は重要でない）は合っている。理由は aggregation ではない。むしろ逆向き。
- aggregation は「`Tool` は `Worker` と関係なく存在できる」関係。単体で存在するものを単体でテストするのは自然
- 単体テストの価値が低いのは composition の側（`Position` は `Worker` の外に出ない）
- 本当の理由は、規模が小さいことと、A でも `Tool` が `Worker` の名前しか知らずに済むこと
- 前職で重視されていたのは、結合のコストが規模・寿命・人数に比例して大きくなるから

### 疑問 8: MVP として考えると、拡大を見据えて依存を少なくしたほうがいいのではないか
最初の理解: そう考えると、やっぱり二重管理はナンセンスな気がする。今は実装の方をシンプルにして、tool を worker 以外が持ち始めたときに設計を変えてもらうのがいいのかな？

答え: その判断でいい（YAGNI）。
- 予想は外れる。`Worker` 以外も道具を持つようになったら、B（全 `Worker` のリスト）も使えない。必要なのは第 3 の形
- B も、プログラム全体で共有されるリストへの依存を増やす
- 「後で変える」を安くする条件は、更新を 1 つの関数に閉じ込めることと、持ち主のポインタを外に見せないこと

（「決めたこととその根拠」のまとめに続く）

### 疑問 9: `tool.updateOwner(owner)` も `worker.giveTool(tool)` も、public だとしても問題ないのでは
最初の理解: どちらも二重管理でも owner は一意になる。

答え: そのとおり。両側をまとめて更新する操作なら public で問題ない。隠す対象は、片側だけを更新する操作。
- 両側そろった public な操作を作ると、その下に片側だけの操作が必ず 1 つ以上ある（`Tool` の中から `Worker` の `tools` を書き換える手段が要るため）
- 両方の入口が互いを呼ぶと、呼び合って終わらなくなる
- 一番単純なのは、本体を 1 つだけにして、片側だけの操作をメソッドとして作らない形。`Worker::giveTool` が本体で、`Tool` が `friend class Worker;` で持ち主の書き換えを `Worker` にだけ許す

（確認の発言なし）

### 疑問 10: 「更新の本体」とは何か。`Tool` 側に置くと何が問題なのか
最初の理解: `tool.giveTo(worker)` でも単体テストは可能だよね？ `Worker.hpp` が必要になる、それの何が問題なんだ？ `worker.getHoge()` ができたところで `Tool` 側のコードには関係しなくないか？

答え: 「更新の本体」は、`tools` と持ち主のポインタを実際に書き換えるコードが入っている関数。今回の課題では、どちらに置いても問題にならない。
- `Tool::use` は純粋仮想関数でテストするものがない。テストが必要なのは `Shovel::use`（`Worker` なしで確かめられる機能）
- `Tool` が壊れるのは、`Tool` が実際に呼んでいる `Worker` のメンバが変わったときだけ。`getHoge()` が増えても影響しない
- 相手の中身を知る箇所の数は、どちらに置いても同じ 1 か所。この依存は置き場所では消せない
- 違うのは向きの数。`Worker` はもともと `tool->use()` を呼ぶので `Tool` を強く知っている

| 本体の場所 | `Worker` → `Tool` | `Tool` → `Worker` |
|---|---|---|
| `Worker::giveTool` | メソッドを呼ぶ（もともとある） | 名前だけ知っている |
| `Tool::giveTo` | メソッドを呼ぶ（もともとある） | メソッドを呼ぶ（新しく増える） |

- この差の重さは、今回はほぼゼロ。`worker.giveTool(tool)` のほうが、依存の向きでも課題文の言い方でも少しだけ筋がいい

最後の自分の言語化:

### 疑問 11: 強い依存を避けるのは、依存先の変更に対しての修正コストが増えるからか

- 同じ原則から出てくる理由: 読むコストが増える・ビルドとテストに要るものが増える・切り離して使えなくなる
- 両方向になると、2 つのクラスが実質 1 つのかたまりになり、片方だけを理解する・直す・テストすることができなくなる
